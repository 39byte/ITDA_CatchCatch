# 선행 연구 — 소비기한 추출 파이프라인의 학술적 근거

> 작성 2026-09-06 · 대상: 요약서 PDF(정성 40점)의 "설계 논리 및 최적화·활용 전략" 원재료
> 제약: 4코어 CPU · GPU 없음 · 오프라인 · **이미지당 ≤ 0.15초** · 평가셋은 비공개 별도 수집

## 0. 이 문서를 읽는 법

7개 영역을 병렬 탐색하고 **모든 인용을 적대적으로 재검증**했다.
결과: **136건 중 CONFIRMED 109 / CORRECTED 27 / FABRICATED 0.**

검증 단계는 실제로 일했다. 잡아낸 오류:
- SVTR 논문의 정확도 표가 **한 행 밀려서** 인용됨
- ARABEX의 연도가 2024 → 실제 **2025** (IJDAR 28(4))
- PP-OCR 파라미터 수 **날조**
- "CORD는 한국어 데이터셋" → **거짓. 인도네시아 영수증**
- Connection Science(DBNet) 논문에 MDPI 2025 논문의 수치가 **검색엔진 혼입**

⚠️ **인용 규칙**: 이 문서에 없는 논문은 요약서에 쓰지 않는다. 여기 실린 것도 §10의 주의사항을
먼저 읽고 쓴다. 검증 없이 인용한 논문 하나가 "엄밀성" 항목 전체를 깎는다.

## 1. 세 가지 핵심 발견

### 1-1. 기성 OCR을 그대로 쓰면 예산의 9~13배다

**PaddleOCR 3.0 공식 벤치마크** (ONNX Runtime, Intel Xeon Gold 6271C):

| 설정 | 이미지당 |
|---|---|
| PP-OCRv5_**mobile**, 기본 (min_736) | **1.75 초** |
| PP-OCRv5_mobile, 가장 공격적 (max_640) | **1.31 초** |
| PP-OCRv5_server, max_640 | 2.95 초 |

`mobile`은 **모델이 작다는 뜻이지 빠르다는 뜻이 아니다.** 그리고 저 스레드 수는 우리 4개보다
많을 가능성이 높다.

**원인**: 그들의 파이프라인은 **검출된 모든 텍스트를 인식**한다. 우리 데이터는 이미지당 글자
연결성분 중앙값 88개(직접 측정), 텍스트 라인 20~60줄이다. 줄당 20~30 ms면 그것만 1~2초다.

> **이것이 Stage 2 박스 필터가 최적화가 아니라 구조적 필수인 이유다.**
> 0.15초는 **크롭을 1~3개만 인식할 때에만** 성립한다.

### 1-2. 문헌의 공백 자체가 설계 근거다

> **4코어 x86에서 스레드 수를 명시하고 detect+recognize 전체를 150 ms 이내로 보고한 논문은
> 존재하지 않는다.** 확인된 "real-time"·"lightweight" OCR 주장은 전부 (a) GPU FPS이거나,
> (b) 단일 모듈만이거나, (c) 4개보다 훨씬 많은 스레드였다.

검색 실패가 아니라 실제 공백이다. → 요약서: *"기성 SOTA를 이식하는 대신 과제 특화 파이프라인을
설계해야 했던 이유."*

### 1-3. 이 과제의 본질은 인식이 아니라 선별이다

**Seker & Ahn (ESWA 2022)** 의 검출기는 날짜 영역 하나가 아니라 **네 가지 마크 클래스**
(date / due-mark / production-mark / code-mark)를 출력한다.
→ **필드 선별이 후처리가 아니라 라벨 공간에 속한다는 공개된 근거.**
우리는 이 의미론을 유지하되 세 번째 CNN을 규칙으로 대체한다.

## 3. 속도 — 0.15초 예산의 근거

### 3-1. 직접 측정한 디코딩 비용 (4코어 고정)

| 코호트 | 비중 | 전체 디코딩 | `draft()` | `draft(720)` |
|---|---|---|---|---|
| 640×640 | 33.0% | 6.8 ms | 7.1 ms | — |
| <1MP | 18.8% | 23.2 ms | 28.2 ms | — |
| 1–4MP | 28.4% | 62.2 ms | 54.7 ms | — |
| **≥4MP** | **19.8%** | **318.1 ms** | 152.5 ms | **103.4 ms** |
| **가중 평균** | | **64.7 ms (예산의 43%)** | **41.3 ms (28%)** | |

**≥4MP 이미지는 전체 디코딩만으로 예산의 2배를 쓴다.**
`draft(720)`이 최적점 — DCT 스케일이 거칠면서도 **모든 대용량 이미지가 1008px 이상**으로 남는다
(`draft(480)`은 3%가 960px 아래로 떨어진다).

→ **PIL `draft()` / `cv2.IMREAD_REDUCED_*` / libjpeg-turbo `scale_denom`은 최적화가 아니라 필수 요건.**
(이건 공학 조치이지 논문이 필요한 문제가 아니다 — 직접 측정치로 방어한다.)

### 3-2. 예산 배분

| 항목 | 비용 | 근거 |
|---|---|---|
| 디코딩+EXIF+리사이즈 | 41 ms | 위 측정 |
| 검출 @960px | 28 ms | 자체 측정(모바일급 CNN, 4스레드) |
| DB 후처리 | ~9 ms | DB 논문: 추론의 약 30%, CPU 바운드 |
| 인식 (크롭 2~3개) | ~20 ms | 자체 측정 7.1 ms/크롭 |
| 파싱+선별 | ~5 ms | 순수 파이썬 |
| **합계** | **~103 ms** | 여유 47 ms |

### 3-3. 소형 검출기 CPU 실측 (직접 검출 경로의 근거)

| 모델 | mAP | 입력 | 하드웨어 | 지연 |
|---|---|---|---|---|
| **NanoDet-Plus-m** | 27.0 | 320px | **Intel i7-8700** | **5.25 ms** |
| NanoDet-Plus-m | 30.4 | 416px | 동일 | 8.32 ms |
| PicoDet-S | 30.6 | 320px | 모바일 ARM | ~8.1 ms |
| YOLO11n | — | 640px | CPU ONNX(하드웨어 미명시) | 56.1 ms |
| YOLOv8n | 37.3 | 640px | CPU ONNX(하드웨어 미명시) | 80.4 ms |

- **Cui, C. 외 (2021). PP-LCNet: A Lightweight CPU Convolutional Neural Network. arXiv:2109.15099** —
  Xeon Gold 6148, MKLDNN, batch=1, **10스레드**. 방법론이 우리와 가장 유사하나 스레드가 2.5배.
- **Chen, J. 외 (2023). Run, Don't Walk: Chasing Higher FLOPS for Faster Neural Networks (FasterNet).
  CVPR 2023, arXiv:2303.03667** — depthwise conv는 FLOP은 싸지만 **메모리 대역폭 바운드**.
  **FLOPs를 줄여도 CPU 지연이 안 줄어드는 이유의 정식 설명.**
- **Li, C. 외 (2022). PP-StructureV2. arXiv:2210.05391** — PicoDet + FGD 증류로 **동등 mAP에 11배 가속**.

### 3-4. 양자화

- **INT8 + VNNI: FP32/AVX-512 대비 ~3.7×, VNNI 없는 AVX-512 INT8 대비 ~2.3×** (Intel 공식).
  **가장 신뢰할 수 있는 단일 레버.**
- ⚠️ **FP16 절대 금지** — §10 참조.

## 6. 블랙박스 평가셋 — 라벨 없이 성능을 추정하는 법

**이번 탐색의 가장 실질적인 수확.** 리더보드가 없어도 OOD 정확도를 *추정*할 수 있다.

### 직접 검출 경로를 택할 경우의 위험

- **arXiv:2601.09497 — Towards Robust Cross-Dataset Object Detection Generalization under Domain
  Specificity**: *"transfer within the same setting type is relatively stable, while transfer across
  setting types drops substantially."* **좁은 도메인으로 학습한 검출기가 다르게 수집된 셋에서 가장
  심하게 무너진다** — 우리 블랙박스 상황 그대로.
- **arXiv:2604.08230** — 세 실패 메커니즘(feature / proposal / proposal-to-label misalignment)이
  전부 "다른 조명·다른 인쇄 폰트·다른 크롭 관행"에 적용된다.
- → 완화책은 **박스 개수가 아니라 시각적 다양성**(브랜드·포장·조명)의 극대화.

## 10. ⚠️ 인용 시 주의 — 따라가면 손해 보는 것

1. **FP16 양자화 금지 (직접 증거 있음).**
   ONNX Runtime 이슈 #10919 / #17033 / #25824 / #22242, PR #21183: x86에 AVX512-FP16이 없으면
   Cast 노드로 FP32 승격. 한 이슈는 **캐스팅이 전체 추론의 53.95%** 로 측정. ARM에서 FP32 대비
   4배 느림 사례도 있다. Peng et al.(2025)의 FP16 권고는 **ARM 모바일·에너지 최적화** 맥락이다.
   → **INT8 또는 FP32만.**
2. **DB의 62 FPS를 인용하지 말 것.** GPU(1080ti, 단일 스레드) 수치다. CPU 채점 대회 문서에 쓰면
   GPU/CPU를 혼동한 것으로 읽힌다. 대신 **후처리가 추론의 약 30%**라는 수치를 쓴다.
3. **EfficientFormer의 1.1 ms는 iPhone NPU다.** CPU 근거로 인용 금지.
4. **MobileOne의 대표 수치도 iPhone.** x86 수치는 미검증 — 인용 보류.
5. **모든 지연 수치의 스레드 수를 확인할 것.** PP-LCNet은 10스레드, PP-OCR 모듈 표는 8스레드.
   우리는 4다.
6. **SVTR은 RNN 단계를 없앤 것이지 CTC를 없앤 게 아니다.** PP-OCR의 SVTR-LCNet은 CTC로 학습·디코딩한다.
7. **CORD는 한국어가 아니라 인도네시아 영수증이다.** (NAVER가 만들었을 뿐) "한국어 레이아웃 KIE가
   확립된 과제"의 근거로 쓸 수 없다. 공개된 CORD-v1은 1,000장이지 11,000장이 아니다.
8. **Connection Science(DBNet) 논문과 MDPI 2025 논문의 수치를 교차 인용하지 말 것.**
   검색엔진이 F1=0.9303 / 63 ms GTX1080을 양쪽에 붙이는 현상이 확인됐다.
9. **ExpDate의 4-클래스 분류는 프로젝트 페이지 기준 확인**이다(본문은 유료). 출처를 그렇게 명시한다.
10. **ARABEX는 2025년, IJDAR 28(4):555–572.** DOI 스템의 `-024-`는 온라인 선공개 연도다.

## 13. 미해결 — 직접 측정해야 하는 것

문헌이 답을 주지 못해 **우리가 재야 하는** 항목:

1. **4코어 x86·스레드 고정·ONNX·320px에서 NanoDet/PicoDet 단독 지연** — 어느 논문도 이 수치를 주지 않는다.
2. **입력 해상도 대 검출 재현율 곡선** — 깨끗한 정량 곡선이 문헌에 없다. 게다가 우리 도메인
   (포장에 찍힌 작은 스탬프)은 ICDAR 자연 장면 텍스트와 다르게 거동한다.
3. **단일 클래스 nano 검출기의 라벨 수 대 mAP 곡선** — FSOD 문헌은 1/5/10-shot만 다룬다.
   100/200/400 박스 구간의 답이 없다 → 직접 ablation.
4. **INT8 동적 양자화의 실제 이득** — Intel의 3.7×는 일반 커널 수치이고,
   Ahn et al.(2023)의 3.3×는 *분류*·*offline 시나리오* 측정이다. 우리 모델에서 직접 잰다.
