## 2. 대회 제약 → 설계 원칙

| 제약 | 설계에 미치는 결과 |
|---|---|
| **4코어 CPU / GPU 없음 / 인터넷 차단** | 모바일급 ONNX 모델만. 가중치는 로컬 파일 경로로만 로드 |
| **2400초 총 벽시계 (import·로드·전 이미지·저장 포함)** | 이미지당 예산은 평가셋 크기 N에 좌우되는데 **N이 비공개** → 2-pass 적응형 구조로 N에 무관하게 만든다 (§5) |
| **⚠️ 이미지당 ≤ 0.15초 (확정 요구사항)** | 아래 §2-1 참조. 이 한 줄이 모델 선택과 크롭 수를 전부 결정한다 |
| **평가셋은 비공개 별도 수집셋** (배포 3,352장의 split 아님) | 배포셋 과적합이 최대 위험. 팀이 직접 찍은 사진이 유일하게 분포가 맞는 검증 신호 |
| **리더보드 없음 · 이메일 제출** | 마감 전 정확도 신호 = 자체 라벨 검증셋뿐. 라벨링은 선택이 아니라 필수 인프라 |
| **Python 3.10 / requirements.txt에 명시된 것만 설치** | 개발은 Windows, 채점은 Linux — 깨끗한 py3.10 환경에서 재현 검증 필수 |
| **정확도 50 / 속도 10 / 정성 40 / 가산점 5** | 요약서 PDF와 자체 수집 데이터가 시간당 수익률 1위 |

### 2-0. 정확도 50점의 내부 산식 (확정) — 전략을 가른다

```
year 5  +  month 5  +  day 5  +  final_date 35  =  50
```

| 상황 | 점수 |
|---|---|
| 전부 정답 | **50** |
| 하나 틀림 | **10** (남은 두 필드 5+5) |
| 둘 틀림 | 5 |
| 셋 틀림 또는 전부 NONE | **0** |

**완전일치가 70%(35/50)로 지배적이지만, 부분점수 15점(30%)이 실재한다.** 두 가지가 확정된다:

1. **기권은 언제나 손해다.** NONE은 네 칼럼 모두 0점인데 **연도만 맞아도 5점**이므로,
   추측의 기대값이 **엄밀히 양수**다. (기존의 "오답과 NONE이 같은 0점"이라는 약한 논거보다 강하다.)
2. **부분 추출 경로가 필수 요구사항이 된다.** 완전 파싱이 실패해도 **연·월만 내면 10점**이다.
   `2027.06.2?`처럼 일자만 안 읽히는 경우 일자를 반반으로 찍어도
   기대값 `10 + 0.5×40 = 30점` > 포기 `10점`. **항상 찍는다.**

### 절대 0점 트리거
타임아웃 · CSV 없음/빈 파일 · `index=False` 누락 · 런타임 가중치 다운로드 · 경로 하드코딩 ·
`input()` 잔존 · 저장소 접근 불가

### 2-1. ⚠️ 0.15초/장 — 예산 재계산

> 학술적 근거 전문은 **`선행연구.md`** 참조. 아래는 결론만.

**기성 OCR을 그대로 쓰면 예산의 9~13배다.** PaddleOCR 3.0 공식 벤치마크(ONNX Runtime,
Xeon Gold 6271C): PP-OCRv5_**mobile** 기본 설정 **1.75 s/img**, 가장 공격적인 max_640에서도
**1.31 s/img**. `mobile`은 모델이 작다는 뜻이지 빠르다는 뜻이 아니다.

원인은 명확하다 — **그들은 검출된 모든 텍스트를 인식한다.** 우리 데이터는 이미지당 글자
연결성분 중앙값 88개(실측), 텍스트 라인 20~60줄. 줄당 20~30ms면 그것만 1~2초다.
⇒ **Stage 2 박스 필터는 최적화가 아니라 구조적 필수다. 0.15초는 크롭을 1~3개만 인식할 때에만
성립한다.**

**디코딩 비용 실측 (4코어 고정)**

| 코호트 | 비중 | 전체 디코딩 | `draft(720)` |
|---|---|---|---|
| 640×640 | 33.0% | 6.8 ms | — |
| <1MP | 18.8% | 23.2 ms | — |
| 1–4MP | 28.4% | 62.2 ms | — |
| **≥4MP** | **19.8%** | **318.1 ms** | **103.4 ms** |
| **가중 평균** | | **64.7 ms (예산의 43%)** | **41.3 ms (28%)** |

**≥4MP 이미지는 전체 디코딩만으로 예산의 2배를 쓴다.** `draft(720)`이 최적점 — DCT 스케일이
거칠면서도 모든 대용량 이미지가 **1008px 이상**으로 남는다(`draft(480)`은 3%가 960px 아래로 떨어짐).
⇒ **`draft()` / `cv2.IMREAD_REDUCED_*`는 선택이 아니라 필수 요건.**

**예산 배분**: 디코딩 41 + 검출@960px 28 + DB 후처리 9 + 인식(크롭 2~3개) 20 + 파싱·선별 5
= **약 103 ms**, 여유 47 ms. 1600px 검출(66ms)이나 크롭 10개(71ms)는 예산을 깬다.

### 구성
| 항목 | 값 |
|---|---|
| 총 | 3,352장, **라벨 없음**, 완전중복 0건 |
| **640×640 레터박스** | **1,106장 (33%)** — 다운스케일된 별도 소스, 날짜 글자 ~14px |
| 고해상 | 4032×3024 260장 … 최대 5712×4284 |

| 배치 편차 | id 1~499는 전부 고해상(중앙값 12MP), id 500+ 는 45%가 640×640 → **최소 2개 소스 병합** |
| EXIF Orientation=6 | 293장 (8.7%) |
| EXIF 촬영일시 | 525장(16%) — **2025-10(413), 2025-12(95)** vs 2021-02/03(12) |

### ⚠️ "90° 회전 문제"는 사실 EXIF 문제다
표본 조사에서 회전으로 지목된 고해상 이미지(000060·000115·000170·000225·000665·000775·000830)는
**전부 EXIF Orientation=6**이었다. `ImageOps.exif_transpose()` 한 줄로 해결되며
**90°/270° 전체 이미지 TTA는 불필요**하다. (640군은 EXIF가 제거됐지만 이미 정방향으로 전처리됨.)

### ⚠️ 평가셋의 연도는 2026~2028에 쏠릴 것이다
EXIF 촬영 시점이 2025-10/12에 몰려 있고 2021 클러스터는 과거 배치의 산물이다. 운영진이 2026년에
새로 구축한 평가셋은 최근 연도로 쏠린다. **배포셋에서 학습한 연도 분포를 쓰면 안 된다.**
연도는 넓은 유효구간 **[2018, 2032]** 로만 검증한다.

### 이미지 품질 / 비용
- 저대비 2%, 흐림 2% → **전역 보정 불필요**, 보정은 크롭 단위로만
- 글자 밀도: 1000px 기준 연결성분 중앙값 **88개**, p90 213개 (텍스트 20~60줄)
  → **검출 박스를 전부 인식기에 넣으면 예산 초과.** 인식 전 필터링이 속도의 핵심
- 텍스트 세로 분포 균일(0.18/0.22/0.25/0.21/0.14) → **"하단만 크롭" 휴리스틱은 통하지 않는다**
- 디코딩+EXIF+리사이즈 가중평균 64.7ms/장, `draft(720)` 적용 시 41.3ms
  → ⚠️ **0.15초 예산에서는 이것만으로 28%다. 병목이다.** 상세는 §2-1

### 연산 비용 (4코어 affinity 고정 실측)
| 워크로드 | 1스레드 | 2스레드 | 4스레드 |
|---|---|---|---|
| 검출기급 CNN @960px | 35.7ms | 26.0ms | 28.4ms |
| 검출기급 CNN @1280px | 68.7ms | 45.6ms | 42.8ms |
| 검출기급 CNN @1600px | 112.5ms | 69.4ms | 66.0ms |
| CRNN 인식기 @48×320 크롭 | — | — | **7.1ms** |

→ **스레드 스케일링은 2에서 포화** (2 vs 4가 거의 동일) ⇒ **2 workers × 2 threads**가
1×4보다 유리할 가능성이 높다(실제 엔진으로 재측정, 4코어 벽시계 20% 이상 개선될 때만 채택).
→ **인식기는 싸다**(크롭당 7.1ms) — 자체 인식기 미세조정은 *속도* 문제가 아니라 오직 *학습 시간* 문제다.
→ ⚠️ **1600px 경로는 0.15초 예산에서 삭제됐다**(66ms = 예산의 44%). 검출 상한은 960px.

### 날짜 표기 유형 (62장 표본)
- `YYYY.MM.DD`(점) ~65%. 뒤에 시각·로트코드가 **구분자 없이** 붙는다: `2021.08.02E`,
  `2021.02.08B5`, `까지01`, `21.09.17까지RT F2`
- 그 외: `YY.MM.DD`(19%), `YYYY/MM/DD`, `YYYY-MM-DD`, `YYYY MM DD`, `DD.MM.YYYY`,
  `DD/Mon/YYYY`(`11/Oct/2021`), `MON DD YY`(`JUL 22 21`), **일자없음** `OCT. 2021`,
  **연도없음** `02.18까지`, 로트코드에 묻힌 `L 095 E 28 10 21`
- 키워드: `까지`(최다) `유통기한` `소비기한` `제조일자` `부터` `EXP` `BBE` `BBD` `BEST BEFORE`
  — **26~39%는 날짜 옆에 키워드가 전혀 없다**
- **약 10%는 날짜 2개** (제조+소비 / 부터+까지) → **항상 나중 날짜가 정답**
- 오답 후보(71%): 품목보고번호, 바코드 `880…`, 전화 `080-`/`1899-1494`/`1399`,
  특허 `10-1855891-0000`, 로트코드, 영양성분, 매대 가격표, `SINCE 1986`,
  안내문구 `유통기한: 하단 표기일까지`
- 인쇄: 잉크젯 도트매트릭스 기본, 어두운 띠 위 흰 잉크, 캔 뚜껑 레이저 각인, 저대비 음각,
  금박, 곡면 26%, 반사광
- 정답이 진짜 NONE인 이미지는 **사실상 없다** (모든 사진이 날짜가 보이게 촬영됨)

## 4. 엔진 선택

| 엔진 | 판정 |
|---|---|
| **RapidOCR (`rapidocr-onnxruntime==1.3.24` + `onnxruntime==1.17.3`)** | **1순위.** 순수 onnxruntime, 로컬 경로 명시 로드, 코드 경로에 다운로드 로직 자체가 없음. **휠 14.91MB = 모델 번들 확증에 가까움** → torch 삭제 가능 |
| EasyOCR (`1.7.2`) | 폴백. `craft_mlt_25k.pth` + `korean_g2.pth` **둘 다** 배치 + `download_enabled=False` 필수 |
| PaddleOCR **3.x** | **금지.** 로컬 `*_model_dir` 명시에도 모델 호스팅 접속 시도 이슈 다수(#16620/#16639), CPU 60초/장 보고 사례 |
| PaddleOCR 2.7.3 | 한국어 인식이 꼭 필요할 때만. `paddlepaddle==2.6.2`와 함께 |

버전 함정: `onnxruntime>=1.18`은 numpy>=2 요구 → **`ort==1.17.3` + `numpy<2`로 통일**.
엔진은 **config dict의 한 줄로 교체 가능**하게 둔다.

### 모델 티어 — 근거 있는 선택 (`선행연구.md` §3)

| 구성 | 선택 | 근거 |
|---|---|---|
| 검출기 | **mobile 계열만** | PaddleOCR 모듈 문서(Xeon Gold 6271C, **8스레드**): mobile_det 79.0 Hmean / 57.77–28.15 ms / 4.7 MB vs **server_det 83.8 / 383.15 ms / 84.3 MB**. **지연 6.6배를 Hmean +4.8에 사는 셈** — 기각 |
| 인식기 | **한국어 mobile rec** | PP-OCRv3 논문 Table 4: **SVTR-Tiny 97.0 ms vs SVTR-LCNet(h48) 7.6 ms** (CPU). 12.8배. server_rec(31.21ms/크롭)은 크롭 3개면 94ms로 예산 초과 |
| 방향 | PP-OCR **cls** 분류기 | ~5ms/크롭. 직접 180° TTA를 짜는 것보다 싸고 정확 |
| 양자화 | **INT8 동적 양자화만** | INT8+VNNI가 FP32/AVX-512 대비 ~3.7×. **가장 신뢰할 수 있는 단일 레버** |

### ⚠️ 양자화 — FP16 절대 금지 (직접 증거 있음)

ONNX Runtime 이슈 **#10919 / #17033 / #25824 / #22242**, PR **#21183**: x86에 AVX512-FP16이 없으면
Cast 노드로 FP32 승격한다. 한 이슈는 **캐스팅이 전체 추론 시간의 53.95%** 로 측정했고, ARM에서
FP32 대비 4배 느림 사례도 있다. Peng et al.(*Algorithms* 2025)의 FP16 권고는 **ARM 모바일 ·
에너지 최적화** 맥락이므로 우리에게 이식되지 않는다. → **INT8 또는 FP32만.**

### ⚠️ 문서에 쓰면 안 되는 수치

- **DB의 62 FPS** — GPU(1080ti, 단일 스레드)다. CPU 채점 대회 문서에 쓰면 GPU/CPU 혼동으로 읽힌다.
  대신 **"후처리가 추론의 약 30%"** 를 쓴다(4코어에서는 더 나빠진다 — binarize/contour/unclip이 CPU 바운드).
- **EfficientFormer 1.1 ms** — iPhone NPU다.
- **MobileOne 대표 수치** — iPhone이다. x86 수치는 미검증.
- 모든 지연 수치의 **스레드 수**를 확인할 것 — PP-LCNet 10스레드, PP-OCR 모듈 표 8스레드, 우리는 4다.
- **PP-OCRv6에는 한국어 인식기가 없다.** v6의 빠른 티어는 우리가 쓸 수 없다.

## 5. 파이프라인 아키텍처 — 2-pass 적응형

```
                    ┌──── Pass A: 전 이미지, 값싼 고정 설정 (~75~85% 확신 후보 확보)
이미지 → [0]정규화 →┤
                    └──── Pass B: Pass A 실패분만, 남은 예산 전부를 계단식으로 소모
```

**왜 2-pass인가**: 평가셋 크기 N이 비공개다. 단일 설정은 N을 잘못 가정하면 타임아웃(0점)이거나
예산을 남기고 끝난다(정확도 손해). 2-pass는 **속도와 정확도를 같은 노브로 만든다** — N이 작으면
자동으로 구조 단계가 더 돌고, N=3352면 Pass B가 자동으로 생략된다. 요약서 2페이지의 핵심 슬라이드.

**정식 명칭과 근거** (자세히는 `선행연구.md` §5):
- **interruptible anytime algorithm** (Russell & Zilberstein, IJCAI 1991) — Pass A 종료 시점부터
  완전한 유효 CSV가 존재하고 이후 계속 개선된다.
- **budgeted batch classification** (Huang et al., MSDNet, ICLR 2018) — *"a fixed amount of computation
  is available to classify a set of examples that can be spent unevenly across easier and harder inputs."*
  **N이 미지인 예산의 정확한 정의.** 우리는 이걸 **디코딩 비용 축**으로 구현한다 — 디코딩 비용은
  추론 *전에* 알 수 있으므로(해상도·파일 크기), 640 코호트(7ms)에는 인식 예산을 더 주고
  ≥4MP 코호트(103ms)에는 덜 준다.
- ⚠️ **"early-exit"라고 부르지 말 것.** 그 용어는 한 네트워크 내부의 깊이별 분기(BranchyNet)를 뜻한다.
  우리는 분리된 모델을 쓰는 **2단계 캐스케이드**다. 문헌을 아는 심사자에게 걸린다.

**Pass B 트리거는 절대 임계값이 아니라 상대 임계값이다.**
Ovadia et al.(NeurIPS 2019): 분포 이동에서 정확도와 캘리브레이션이 함께 무너지고 사후 캘리브레이션은
*"does indeed fall short"*. 평가셋이 2026년 별도 수집이므로 배포셋에 맞춰 튜닝한 신뢰도 임계값은
어긋난다. → **"신뢰도 < 0.6"이 아니라 "신뢰도 하위 k%"를 재처리하고, k는 남은 벽시계로 정한다.**
임계값이 이동해도 예산이 자동 소진되고 타임아웃도 없다.
(Jitkrittum et al., NeurIPS 2023: 신뢰도 기반 캐스케이드가 실패하는 세 체제 중 하나가 분포 이동이다
— 게이트를 신뢰도 하나에 걸지 말 것.)

⚠️ **0.15초 제약 하에서 Pass B의 지분**: 예산 여유가 47ms뿐이므로 Pass B는 "남은 예산 전부"가
아니라 **예산의 명시적 소수 지분**으로 운영한다. Pass A가 예산을 초과하면 Pass B는 0이 된다.

### [0] 정규화
- `ImageOps.exif_transpose()` **무조건 먼저**
- 대용량 JPEG는 `draft()`로 DCT 단계 축소 디코딩
- ⚠️ **검출 해상도 ≠ 인식 해상도** — 이걸 틀리면 큰 코호트가 통째로 날아간다.
  12MP(4032px) 이미지를 960px로 줄이면 40px 날짜 스탬프가 **9.5px**이 된다. 인식 불가능하다.
  **검출은 축소본에서 싸게 하고, 박스 좌표를 원본으로 되돌려 원본 픽셀에서 크롭한다.**
  640×640군은 되돌릴 원본이 없으므로 **크롭을 2~4× LANCZOS 업스케일**한다. **코드 경로 2개.**
- **검출 해상도 상한은 960px.** 1600px 경로(66ms)는 0.15초 예산에서 삭제한다.
  long side를 `[960, 960]`으로 클램프 — 작은 이미지는 올리고 큰 이미지는 내린다.
- **디코딩은 `draft(720)` 필수.** ≥4MP 코호트가 318ms → 103ms.

### [1] 검출
DB 계열 검출기 1회, 축소본(≤960px)에서. 텍스트 세로 분포가 균일하므로 전체 프레임 검출이 필수.

### [2] 박스 필터 — **속도의 핵심이자 이 설계가 성립하는 유일한 이유**
글자 밀도가 높아(중앙값 88 성분) 전부 인식하면 **어떤 모델을 써도** 예산 초과다
(PaddleOCR 기본 파이프라인이 1.31~1.75 s/img인 이유가 정확히 이것 — §2-1).
인식 전에 값싼 신호로 거른다: 박스 종횡비·높이 / 이진화 후 획 밀도·잉크 비율 /
연결성분 수·간격 규칙성.

**상위 K개만 인식기로 — K = 2~3.** (기존 8~15에서 하향. 0.15초 예산의 직접 결과.)
튜닝 목표는 **Viola & Jones의 캐스케이드 규칙**: 싼 단계는 **재현율을 거의 1로** 맞추고
오탐률은 느슨하게 둔다. 정밀도는 Stage 5가 회수한다.

### [3] 인식 (크롭 단위)
- **Pass A에서는 1변형만.** 크롭 변형 4종은 4×7.1ms = 28ms로 예산을 깬다
  → **다변형은 Pass B 전용**(§[5]).
- **모폴로지 클로징이 1순위 변형**: `cv2.morphologyEx(bin, MORPH_CLOSE, (2,2)~(3,3))`가
  끊긴 점을 획으로 잇는다. ARABEX(IJDAR 2025)가 학습된 오토인코더로 하는 일의 값싼 대응물 —
  **인식기 미세조정(25시간)이 사려는 이득의 상당 부분을 2시간에 산다.** 커널은 고정 3×3이 아니라
  **도트 피치에 맞춰** 정한다.
- 180° 뒤집힘은 **PP-OCR의 방향 분류기(cls, ~5ms/크롭)** 를 쓴다. 직접 TTA 짜지 말 것.
- ⚠️ **TTA 집계 주의** (Shanmugam et al., ICCV 2021): *"even when TTA produces a net improvement in
  accuracy, it can change many correct predictions into incorrect predictions."*
  → 변형 결과를 다수결로 뭉개지 말고 **유효 날짜로 파싱되는지를 1차 게이트**로 쓰고,
  신뢰도는 그 다음에 본다.

### [4] 파싱
- OCR 혼동 정규화: `O→0, l/I→1, S→5, B→8, Z→2, 、→.`
- **박스 병합 후 파싱**(빠뜨리기 쉬운 필수 단계): DB는 `2021.` `08` `.02` `까지`로 쪼개서 준다.
  y밴드로 정렬 → 가로 인접 텍스트를 공백 있음/없음 두 가지로 결합 →
  **개별 박스 텍스트와 병합 라인 텍스트 모두에 정규식을 돌린다.**
- 관측된 전 포맷을 커버하는 정규식 패밀리 + 구분자 없이 붙은 시각·로트코드 분리 규칙

### #10 게이트 — (A) 범용 텍스트 검출 vs (B) 날짜 영역 직접 검출

**0.15초 제약으로 이 판단의 무게가 커졌다.** 도메인 문헌은 정확도로 둘을 가르지 못한다 —
ExpDate(B계열) 97.74%, 개선 DBNet(A계열) ~98%. **가르는 건 지연뿐이다.**

그런데 (A)의 치명적 비용은 검출기가 아니라 **"전부 인식"** 에 있었고(§2-1), 그건 Stage 2가 이미
제거한다. 반면 (B)는 학습·라벨링·GPU를 요구하고 **새로운 위험**을 만든다:

> **arXiv:2601.09497** — *"transfer within the same setting type is relatively stable, while transfer
> across setting types drops substantially."* **좁은 도메인으로 학습한 검출기가 다르게 수집된
> 셋에서 가장 심하게 무너진다** — 우리 블랙박스 평가셋 상황 그대로.
> 완화책은 **박스 개수가 아니라 시각적 다양성**(브랜드·포장·조명)의 극대화다.

**따라서 (A)를 주력으로 유지하고, (B)는 측정으로 판정한다** (Day 1~3, 4코어 고정·ONNX·batch=1):

| 측정 | 결정 |
|---|---|
| ① det@960px + ③ 크롭 3개 인식 **≤ 110 ms** | **(A) 확정.** Stage 5와 요약서에 투자 |
| 위가 110 ms 초과 | **(B)로 전환.** 단 다양성 우선 라벨링 + (A) 폴백 경로 유지 |
| M1(국소화 재현율) 0.80~0.92 | 실패가 "스탬프 근처에서 아무것도 못 찾음"(금박·곡면·각인) 위주면 **(A) 박스와 union하는 추가 제안원**으로만 (B)를 쓴다 |
| M1 < 0.80 | 검출 문제가 아니다. **해상도 정책이나 레터박스 처리가 깨진 것** — 그걸 먼저 고친다 |

**(B) 후보의 근거 수치**: NanoDet-Plus-m **27.0 mAP @320px = 5.25 ms (Intel i7-8700)**,
PicoDet-S 30.6 @320px ≈ 8.1 ms(ARM). PP-StructureV2는 PicoDet+FGD 증류로 **동등 mAP에 11배 가속**.
⚠️ **어느 논문도 4코어 x86·스레드 고정 수치를 주지 않는다** — 직접 재야 한다.
⚠️ 단일 클래스 nano 검출기의 **라벨 수 대 mAP 곡선도 문헌에 없다**(FSOD는 1/5/10-shot만 다룸)
→ 100/200/400 박스로 직접 ablation.

### #11을 하지 않는 이유 (산수)
인식은 마지막 고리라 이득이 상류에 곱해진다. 검출 0.85 × 선별 0.80 × 인식개선 0.20 ≈ **13.6%**
≈ **50점 중 +6.8점 / 25시간 = 0.27점/시간**. 반면 선별을 0.80→0.92로 올리면
**+3.8점 / 8시간 = 0.48점/시간**, 새 실패 모드도 0점 리스크도 없다. 게다가 합성데이터+자체 크롭
300장으로 튜닝한 CRNN이 **별도 수집된** 평가셋에 전이된다는 보장이 없다.
→ **요약서의 "향후 고도화 계획"에 넣는다.** 공학 비용 0으로 정성 점수를 얻는다.
모폴로지 클로징(#5)이 같은 이득의 상당 부분을 2시간에 산다.

| 상황 | 하지 말 것 | 할 것 | 기대 점수 |
|---|---|---|---|
| `2027.06.2?` (일자 불명확) | 전부 NONE | 연·월 확정 + 일자 최선 추측 | 10 + 0.5×40 = **30** vs 0 |
| 일자 없음 `OCT. 2021` | 전부 NONE | 연·월 + **말일로 보정** | 최소 **10** vs 0 |
| 연도 없음 `02.18까지` | 전부 NONE | 월·일 + 연도 추론 | 최소 **10** vs 0 |
| 파이프라인 전면 실패 | 전부 NONE | 어디서든 그럴듯한 **연도 하나만** 건져도 | **5** vs 0 |

⇒ **후보를 all-or-nothing으로 다루지 말 것.** 필드 단위로 확신도가 다르면 다른 대로 채워 넣는다.

**단, 요약서 채점 항목에 "오탐 최적화 전략"이 명시돼 있다** — FP는 *정성* 채점 관심사다.
그래서 공짜 차익거래를 한다: **τ=0으로 항상 출력하되, 같은 점수를 문서화된 튜너블 임계값으로 노출**한다.

> "τ=0으로 운영한다. 본 대회 산식(`y5+m5+d5+final35`)에서 NONE은 네 칼럼 모두 0점인 반면
> 부분 정답도 득점하므로, 기권의 기대값이 추측보다 항상 낮기 때문이다.
> 반면 잘못된 날짜가 누락보다 위험한 실제 매대 감사 배포에서는 τ≈0.6을 쓰며,
> 검증셋 기준 커버리지 0.71에서 정밀도 0.94를 얻는다."

이 한 문장 + 정밀도/커버리지 곡선 한 장이면 정량 손실 0으로 정성 점수를 회수한다.

### 보정 메커니즘 (위 표의 "할 것"을 어떻게 구현하는가)

| 케이스 | 구현 |
|---|---|
| 일자 없음 (`OCT. 2021`) | ⚠️ **"말일로 보정"은 틀렸다 — 실물 확인 결과 반증됨.** `001955.jpg`(프랑스 수입 과자)는 일자 자리에 `--`가 인쇄돼 있고, **같은 라벨의 한글 표시사항이 규칙을 명시한다: "제품 별도표시된 Best before: 월/년의 01일까지"**. 즉 정답은 `2021-10-01`이지 `-10-31`이 아니다. ⇒ **① 이미지 안에서 규칙 문구를 먼저 찾고(`01일까지` / `말일까지` / `해당 월` 등) ② 없으면 `01`을 기본값**으로 둔다(수입품의 한글 표시사항이 01일 규칙을 쓰는 사례가 확인됨). 말일 가정은 근거 없음 |
| 연도 없음 (`02.18까지`) | ① EXIF `DateTimeOriginal`이 있으면 **촬영일 직후로 오는 가장 가까운 연도** ② 같은 이미지의 다른 연도 토큰 ③ 코호트 기반 추정 ④ 기본값<br>⚠️ **①은 정작 필요한 이미지에서 거의 발동하지 않는다** — 확인된 두 결측 사례(`000995`, `001955`) 모두 **EXIF 촬영일시가 없다.** EXIF가 있는 16%는 전부 고해상 2025년 촬영본이고, 결측 사례는 재가공된 무EXIF 코호트에 몰려 있다. ⇒ ①에 의존하지 말고 ②③을 실질 경로로 설계할 것 |
| 아무 후보 없음 | 전 필드 NONE (**유일하게 허용되는 기권**) |

**불변식 (CSV 저장 전 assert)**: `final_date == "NONE"` **iff** `year==month==day=="NONE"`.
y/m/d가 채워졌는데 `final_date`를 NONE으로 두면 **35점을 그냥 버리는 것**이고 채점기 파서도 깨뜨린다.
반대로 y/m/d 중 일부만 확신하더라도 **나머지를 추측으로 채워 `final_date`까지 구성**한다 —
어차피 틀려도 잃을 게 없고 맞으면 35점이다.
**검증셋의 NONE 비율이 8%를 넘으면 기권 정책 문제가 아니라 재현율 버그다.**

| 세트 | n | 표본 | 파이프라인 출력 노출 | 용도 |
|---|---|---|---|---|
| **V1 (블라인드)** | 200 | 층화 랜덤, **누구도 출력을 보기 전에** 추첨 | ❌ 빈칸 | 정직한 추정치. **최대 3번만**(D4/D6/D9) 열어보고 **집계값만** 본다 |

**층화 기준**: 소스 코호트(id<500 고해상 / id≥500 비640 / 640×640군) × 해상도 버킷.
**640군은 33% 비중보다 과표집**한다 — 평가셋이 이 코호트 0%일 수도 100%일 수도 있다.

### S 세트가 전략적으로 가장 중요하다
평가셋은 운영진이 2026년에 새로 구축했고, 배포셋의 큰 덩어리는 2021년 배치다.
**팀이 2026년 편의점에서 직접 찍은 사진이 평가셋과 가장 가까운 대리 표본**이다.
가산점 5점은 부수 효과고, 진짜 가치는 "리더보드 없는 대회에서 유일하게 분포가 맞는 검증 신호".
요약서에는 *"평가셋이 별도 수집된다는 점을 고려해 2차 출처 OOD 검증셋을 구축했다"* 로 쓴다 —
판정단에게 "사진 좀 찍었다"가 아니라 실험 설계로 읽히고, 실제로 사실이다.

### 부트스트랩 편향 차단 (4중 통제)
파이프라인이 후보를 낸 이미지만 라벨링하면 **검출 실패 케이스가 검증셋에서 통째로 빠져**
정확도가 검출실패율만큼 부풀려진다.
1. V1은 ID 랜덤으로 뽑는다. 출력 기준 선택 금지. **타협 불가**
2. 보조 UI에서도 **후보가 0개인 이미지가 "추측 없음"으로 반드시 등장**한다. 조용히 건너뛰지 않는다
3. "후보 0개" 비율을 1급 지표로 보고
4. D의 10%를 2인 이중 라벨링. `정확도(D) − 정확도(V1) > 5pp`면 보조 라벨이 도장 찍기다 → V1을 믿고 일부를 블라인드 재라벨링

### 도구: 의존성 0의 정적 HTML 한 장

## 9. 검증 하네스

지표를 모르므로 **매 실행마다 9개를 전부 보고**한다:

1. `final_date` 완전일치 (주 가설)
2. 필드별 정확도(year/month/day)와 그 평균 (부분점수 가설)
3. 4필드 전부 일치 (§7 불변식이 맞으면 #1과 같아야 한다 — 다르면 버그)
4. 커버리지 (`final_date ≠ NONE` 비율)
5. 커버된 것 중 정밀도 → **p2가 요구하는 오탐 수치**
6. **국소화 재현율** — 선별 *전에* 정답 문자열이 후보에 있었던 비율
7. **선별 정확도 = #1 / #6** → **가장 유용한 진단.** Stage 1–2를 고칠지 Stage 4를 고칠지 알려준다
8. **오류 분류 카운트** (정답과 후보 리스트를 대조해 자동 분류):
   후보없음 / 오답후보선택 / 정답후보오독 / 파싱실패 / D-M 모호성 / 연도추론 실패
   → **이 표가 그대로 PDF로 간다.** 어떤 단일 정확도 숫자보다 논리성 점수에 기여한다
9. 벽시계: 총합, p50/p90/p99 초/장, N∈{500,1000,2000,3352} 외삽

추가로 **일수 오차 분포**: 1일 또는 10일 오차 = 숫자 오독, 연 단위 오차 = 엉뚱한 영역. 공짜 진단.

### ⭐ 라벨 없이 OOD 정확도를 추정하는 법 (이번 선행연구의 최대 수확)

리더보드가 없어도 **3,352장 비라벨 데이터만으로** 분포 이동의 크기를 잴 수 있다:

- **Agreement-on-the-Line** (Baek et al., NeurIPS 2022) — **두 모델의 일치율이 OOD 정확도를 예측한다.
  라벨이 전혀 필요 없다.** → 서로 다른 두 설정(인식기 2종, 또는 전처리 변형 2종)을 3,352장 전체에
  돌리고 **일치율**을 추적한다. 일치율이 떨어지는 코호트가 곧 위험 코호트다.
- **ATC** (Garg et al., ICLR 2022) — 비라벨 데이터의 신뢰도 임계값으로 OOD 정확도 추정.
- **Accuracy on the Line** (Miller et al., ICML 2021) — ID/OOD가 강한 선형 상관 →
  **자체 검증셋 최대화가 정당화된다.** 단 **Accuracy on the Curve**(Liang et al., ICML 2023)는
  부분모집단 불균형에서 비선형임을 보인다 → **코호트별 보고가 필수**라는 우리 결론과 일치.
- **Recht et al.(ICML 2019)**: **같은 프로토콜로** 재수집한 테스트셋에서도 ImageNet 11–14% 하락.
  다른 사람이 다른 해에 수집한 우리 평가셋은 **그보다 나쁠 것으로 예산**한다.
- **요약서에 쓸 문장** — Gulrajani & Lopez-Paz(ICLR 2021): *"a DG algorithm without a model selection
  strategy should be regarded as incomplete."* → **"리더보드가 없었다"를 "모델 선택 기준이 우리
  방법의 일부다"로 전환한다.**

### 리더보드 없이 정직하게 홀드아웃하기
- V1은 최대 3번, **집계값만** 본다. 개별 오류는 절대 안 본다. 오류 분석은 전부 D에서.
- **코호트별 분해 보고는 필수** — 모든 지표를 640군/고해상군 따로. 평가셋이 한쪽 100%일 수 있다.
- **헤드라인은 평균이 아니라 최악 코호트 점수로 쓴다.** 평가셋 구성이 미지일 때 가장 강력한
  과적합 방지 장치다.
- **분포이동 시뮬레이션 — 단, 보정해서 써야 한다**: V1의 고해상 이미지를 640×640으로 재인코딩해
  재채점하면 저해상 코호트에 대한 강건성을 미리 잴 수 있다. 그런데 **순진하게 축소하면
  시뮬레이션이 실제보다 쉬운 문제를 낸다.** 직접 측정한 결과:

  | 640 변환 방식 | 실제 640 코호트 대비 고주파 에너지 |
  |---|---|
  | LANCZOS / BOX | 1.68× (너무 선명) |
  | BICUBIC | 1.51× |
  | BILINEAR | 1.30× |
  | **BILINEAR + JPEG q75 + GaussianBlur(σ=0.5)** | **1.00× ✓** |

  실제 640 코호트는 양자화 테이블 평균 **29.0**(≈JPEG 품질 75, 중앙값 48KB)인 반면 고해상
  코호트는 **6.6**이다. 게다가 JPEG 품질만 낮춰서는(q70~90) 거의 움직이지 않았다 —
  차이의 대부분은 압축이 아니라 **리샘플링 소프트니스**다. 즉 640 코호트는 단순히 "작은" 게
  아니라 **해상도가 시사하는 것보다 더 뭉개져 있다**(손실 파이프라인을 한 번 더 거쳤다).
  σ=0.5 블러까지 넣어야 실제 분포와 맞는다. 보정 없이 돌리면 강건하다는 잘못된 확신을 얻는다.

- 나머지 시뮬레이션 축: JPEG 품질 60, ±10° 회전.

- **보고 형식은 Hendrycks & Dietterich(ICLR 2019)의 프로토콜을 따른다** — 가치는 데이터셋이 아니라
  방법이다: 고정 손상 집합을 **등급별 심각도**로 적용하고, 단일 숫자가 아니라 **심각도 곡선**으로
  보고한다. 위 σ 보정값이 그 곡선의 한 축이 된다.
- **구현체는 STRAug** (Atienza, ICCVW 2021) — **36개 증강 함수 / 8개 그룹**
  (warp·geometry·pattern·blur·noise·weather·camera·process), `pip install straug`,
  **CPU 전용 · 라벨 불필요**. 직접 짜지 말 것.
- **경보 임계값**: `D − V1 > 5pp` → 라벨 편향. `V1 − S > 10pp` → 배포셋 과적합.
  코호트 격차 > 10pp → 나쁜 쪽을 최적화.
- **Day 8 동결 규칙**: D에서 2pp 미만 개선하는 규칙은 추가 금지. 변경분은 D9에 V1으로만 재검증.

**노트북 vs 모듈 기준**: *판정단이 p1을 읽다가 보고 싶어할 것*은 노트북에 —

정규식·점수 함수·엔진 래퍼는 모듈에 (단위 테스트 대상이고 `Pool`이 import 가능해야 한다).

cwd 리스크(채점기가 저장소 루트 밖에서 nbconvert를 부르면 `import itda_ocr` 실패)는 실재하지만
**실측 가능한 문제**다. 코드를 노트북에 복제하지 말 것 — 10일간 3명이 만지면 노트북 사본과 모듈
사본이 조용히 어긋나는 쪽이 더 위험하다. `Path.cwd()`와 상위 경로를 훑어 `itda_ocr/`와 `weights/`를
찾는 루트 리졸버를 넣고, **Day 1과 Day 9에 실제 채점 명령으로 증명**한다.

### 셀 구성
| 셀 | 내용 |
|---|---|
| **0** | **템플릿 CONFIG 원문 그대로.** 추가·재정렬 금지. Day 9에 템플릿과 diff |
| **1** | 첫 줄에 `T0=time.time()` → **cv2/onnxruntime import 전에** `os.environ[...THREADS]="4"`(import 시점에 읽는다) → import → `cv2.setNumThreads(4)` → 루트 리졸버 + `sys.path.insert` → `DEADLINE = T0 + 2100` |
| **2** | **config dict** — 코호트별 검출 입력 크기, 업스케일 배수, 임계값, 양/음성 키워드 목록, Pass B 계단 정의, τ를 한 곳에. 이어서 모델 생성 + 가중치 파일 존재 확인과 읽기 쉬운 에러. **판정단이 읽는 셀** |
| **3** | 파일 목록(템플릿의 stem 로직, 정렬) → **전부 NONE인 DataFrame을 만들어 즉시 저장.** 1초 시점부터 유효한 CSV가 존재한다. N과 장당 예산 출력 |
| **4** | **Pass A** 메인 루프. 이미지 단위 `try/except`→NONE. 50장마다 flush. `budget_i=(DEADLINE−now)/(N−i)` 초과 예상 시 단계 하향(TTA off → 검출 해상도↓ → 변형 생략). 전체를 `try/finally` |
| **5** | **Pass B** — Pass A 실패분만, `DEADLINE`까지 계단식 상승 |
| **6** | 조립 → **검증** → 저장. assert: 행수 == 파일수 / 전 셀 `str` / `year` `^\d{4}$\|^NONE$`, `month`·`day` `^\d{2}$\|^NONE$`, `final_date` `^\d{4}-\d{2}-\d{2}$\|^NONE$` / §7 불변식. **실패 시 안전값으로 복구하고 경고만 — 절대 raise 금지.** 그 다음 `df.to_csv(OUTPUT_PATH, index=False)` |
| **7** | 실행 리포트: 커버리지, 경과, 초/장, 단계별 시간, Pass B 사용률. 비용 0이고 채점기가 실행된 노트북을 보관한다 |

**절대 규칙**: 셀 3 이후로는 어떤 경우에도 raise하지 않는다. `tqdm` 고빈도 갱신·matplotlib·`%pip`·
